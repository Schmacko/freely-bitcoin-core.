# FREELY (FLY) approved protocol parameter baseline

**Owner decision:** All four proposal areas were explicitly approved in the project conversation on 18 November 2026.

**Scope:** Approval authorizes implementation and verification of these parameters. It does not authorize a public launch, mining deployment, public RPC/P2P exposure, DNS seed operation, or deployment. The genesis nonce and resulting block hash are derived outputs and remain uncomputed until a reproducible mining procedure completes.

## 1. Proof of work and retargeting

| Parameter | Approved value |
|---|---|
| Hash algorithm | SHA-256d |
| Target spacing | 600 seconds |
| Retarget interval | 2,016 blocks |
| Target timespan | 1,209,600 seconds |
| Minimum actual timespan | 302,400 seconds |
| Maximum actual timespan | 4,838,400 seconds |
| powLimit | `00000000ffffffffffffffffffffffffffffffffffffffffffffffffffffffff` |
| Genesis nBits | `0x1d00ffff` |
| Minimum-difficulty exception | Disabled |
| No-retargeting | Disabled |
| BIP94 | Enabled from genesis |

The approved genesis target decoded from nBits=0x1d00ffff is slightly harder (smaller) than the approved powLimit. The compact target is valid and does not exceed the maximum permitted target; the difference is approximately 0.0015259%. This is a maximum-target boundary, not a security guarantee. Expected work per block at the genesis target is approximately 2^32 hashes. Low total honest SHA-256d hashpower remains vulnerable to majority-hashrate attacks, regardless of correct difficulty adjustment.

Retarget test vectors use previous compact target `0x1c00ffff`:

| Elapsed seconds | Clamped seconds | Expected compact target |
|---:|---:|---|
| 302,399 | 302,400 | `0x1b3fffc0` |
| 302,400 | 302,400 | `0x1b3fffc0` |
| 1,209,600 | 1,209,600 | `0x1c00ffff` |
| 4,838,400 | 4,838,400 | `0x1c03fffc` |
| 4,838,401 | 4,838,400 | `0x1c03fffc` |

Tests must also cover invalid compact targets (negative, zero, overflow, above powLimit), compact round trips, boundary ancestry, non-boundary carry-forward and BIP94 time-warp resistance.

## 2. Network identity

| Parameter | Approved value |
|---|---|
| Chain name / config section | `freely` |
| P2P message start bytes | `fa c3 b7 d1` |
| P2P port | 49444 |
| RPC port | 49445 |
| Data-directory suffix | `freely` |
| P2PKH prefix | decimal 55 / `0x37` |
| P2SH prefix | decimal 117 / `0x75` |
| WIF prefix | decimal 183 / `0xb7` |
| Extended public key version | `0x04464c59` |
| Extended private key version | `0x04666c79` |
| Bech32 HRP | `fly` |

These values must be tested against all built-in Bitcoin network identities, including default signet magic `0a03cf40`, cross-role port collisions and any custom signet magic derived from a configured challenge. Port selection in the dynamic/private range does not guarantee that a port is unused on a particular host. The extended-key versions are custom four-byte values; verify Base58Check round trips and wallet import/export behavior. Do not infer an official BIP44 coin type from these values; request a SLIP-0044 assignment separately if needed.

## 4. Script and deployment policy

| Rule | Approved activation |
|---|---:|
| BIP34 | Height 1 |
| BIP65 | Height 1 |
| BIP66 | Height 1 |
| CSV (BIP68/112/113) | Height 1 |
| SegWit (BIP141/143/147) | Height 1 |
| Taproot / witness v1 | Verify and enforce using the v32.1 script-flag architecture; no separate buried-height field exists in `Consensus::Params` |

The v32.1 source defines buried deployments for BIP34, CLTV, DER signatures, CSV and SegWit. Its `BIP34Hash` may be null for networks activating BIP34 at height 1, as shown by the upstream Testnet4 and Signet parameter patterns. Do not import Bitcoin mainnet's historical BIP34 checkpoint.

The sole version-bits deployment in this v32.1 source is TESTDUMMY:
- bit 28
- start time `NEVER_ACTIVE` (-2)
- timeout `NO_TIMEOUT` (INT64_MAX)
- minimum activation height 0
- threshold 1,815 of 2,016 (90%)
- period 2,016

No experimental deployment is activated. Future consensus upgrades require their own proposal, review, test vectors and explicit owner approval.

## 5. Activation and release safeguards

- Populate the machine-readable manifest with approved values, but leave `genesis.hash` and `genesis.nonce` unset until the final mining output is independently verified.
- Keep FREELY startup fail-closed while the genesis commitment is incomplete.
- A passing manifest validator is not a substitute for C++ integration, compilation, functional tests or security review.
- The production-readiness ledger must not mark G0 or any other gate PASS without its evidence requirements.
- No public launch, DNS seeds, public network exposure or deployment is authorized by this parameter approval.

## 6. Required regression test groups

1. Network magic uniqueness and `GetNetworkForMagic` round trip.
2. P2P/RPC port distinctness and collision checks.
3. Data directory and config section isolation.
4. Base58 P2PKH/P2SH/WIF and BIP32 extended-key encode/decode.
5. Bech32 HRP and witness address round trips.
6. Genesis transaction serialization, txid, Merkle root and header serialization.
7. Genesis proof-of-work target check and fixed hash assertion after nonce is mined.
8. Genesis coinbase is not a spendable UTXO.
9. All approved buried deployment heights and witness script flags.
10. Retarget clamp boundaries, compact target validity, ancestry and BIP94.
